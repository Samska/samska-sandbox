## SS-033 — Admin Catalog Management (#55)

- State changes: The Market at `/` no longer renders Product setup tools or UUID lookup, and its empty state gives customer-facing guidance with no Admin link or call to action. A distinct Admin Product-management surface at `/admin/products` lists Products with ID, name, description, price, and media selection, filters locally by case-insensitive name, distinguishes an empty Catalog from no matches, and provides loading, failure, retry, pending, success, and empty states. It creates Products and edits name, description, price, and optional curated `mediaKey` through `POST` and full-replacement `PUT /api/products/{id}`, and deletes through `DELETE /api/products/{id}` after explicit inline confirmation. A successful create, edit, or delete whose Product-list refresh fails keeps the success message, reports that the change was saved but the list could not be refreshed, and offers a working list retry instead of implying the mutation failed or that the stale list is current. Deletion is refused with `409 Conflict` while the Product is in the current Cart, and the Admin UI explains the conflict with a link to the Market; absent IDs return `404`. The backend routes Cart addition and Product deletion through a neutral `CatalogCartCoordinator` that owns one process-local lock; Catalog never reads Cart storage, and the business-module dependency remains one-way (Cart → Catalog). Frontend routing selects Market, Admin, or a distinct not-found view from `window.location.pathname` using same-origin links, so direct entry, reload, and history work with no router dependency; `/admin/products` is navigation only and provides no access control. Editing a Product does not alter name or unit price already captured in a Cart line, quantity changes and re-adds preserve those captured values, newly added lines use current Catalog values, and Cart remains the single monetary owner. This change also reconciles the stale SS-032 pre-merge wording below.
- Decisions: full-page same-origin navigation instead of a router dependency; full-replacement `PUT` preserving Product identity; atomic per-ID `replace`/`deleteById` in the Product store so an update cannot resurrect a deleted Product; one neutral application coordinator with a shared lock instead of Catalog→Cart coupling or dependency inversion; the guaranteed invariant is single-process API-path only (add first → deletion sees the Cart line and returns `409`; delete first → addition sees no Product and returns the existing `404`), and a Cart removal racing a deletion may conservatively return `409`; no protection is claimed for callers that bypass the coordinator or for future multi-process or persistent deployments; no ADR because the work follows accepted ADR 0001 and introduces no new durable architecture decision; no dependency, global state, persistence, authentication, authorization, or access-control claim.
- Agent Verification: backend `./mvnw --batch-mode --no-transfer-progress clean verify` passed 69 tests (Product update/delete domain, store, API, both add/delete orderings including latch-controlled interleavings, and Cart captured-value regressions); frontend `npm run typecheck`, `npm test` (75 tests across 10 files), and `npm run build` passed; local Vite development and production preview servers served `/`, `/admin/products`, and unknown paths; the API flow through the Vite proxy verified create, update, `409` while in Cart, `204` deletion, `404` after deletion, and captured Cart values.
- Human Verification: Passed on 2026-09-23 based on the owner's report that the listed scenarios were tested in the browser and no problems were found. This is owner-reported human evidence and remains distinct from Agent Verification and CI Verification.
- Delivery: PR [#56](https://github.com/Samska/samska-sandbox/pull/56) carries the SS-033 implementation and is the authoritative CI record; CI Verification must be successful on the exact final PR head before merge, and merge requires explicit owner authorization.
- Next step: complete review and CI on the pull request and merge only after explicit owner authorization.

## SS-032 — Implement Checkout vertical slice (#53)

- Completed and merged via PR #54 (squash commit `20b7d537`): Checkout is an editable live view of the current authoritative Cart. Entering Checkout is a local view transition that creates no backend resource; the surface renders the shared editable Cart item row, and `Catalog` remains the single owner of Cart state, so every server response updates quantities, line subtotals, and total. ## Local Development Launcher Maintenance (#50)

- Completed and merged via PR #51 (squash commit `729063e`): `scripts/dev.sh` verifies process-group ownership without `ps`, treats a valid `JAVA_HOME` as the authoritative Java selection and normalizes it before appending `/bin` exactly once to the `PATH` it prepends for child processes, refuses to start when the required backend (8080) or frontend (5173) port is already in use, and accepts backend health only while its own backend process group is running.
