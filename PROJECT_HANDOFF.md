## SS-034 — Product Media Upload (#57)

- State changes: The Admin Catalog surface is split into three route-based screens. `/admin/products` is a compact management-only list with a heading, a prominent Create Product action, the existing case-insensitive name search, a result count, and dense rows (thumbnail, name, concise image state, price, Edit link, Delete with inline confirmation); create and inline edit forms are gone from the list. `/admin/products/new` is a dedicated centered creation form with Name, Description, Price, and a staged Product image section that previews a selected JPEG locally, explains limits and the EXIF limitation, and can clear the selection; it creates first with `mediaKey: null` and then uploads, reporting "Product created; image could not be uploaded." with retry and never offering another create. `/admin/products/{id}/edit` is a matching form that shows the current image first (uploaded, then mapped curated, then monogram), stages replacement or confirmed removal, distinguishes selected from saved media, reports field/media partial success for the separate requests, reconciles uncertain network outcomes by reading the Product, and discards unsaved choices on Cancel. The curated-image dropdown is removed from both forms; an existing exact `mediaKey` is preserved through full `PUT`, a mapped key still displays its image after upload removal, and new Products use `mediaKey: null`. Products gain a read-only nullable `uploadedMediaId`; uploaded media takes display precedence on Market cards and Product detail, removal reveals the retained curated asset or the monogram fallback, and full Product `PUT` preserves uploaded media. Uploads are validated server-side by content signature, decoded dimensions, and pixel budget, then re-encoded before publication, against fixed limits: 3 MiB multipart request, 2 MiB input file, 2048 pixels per side, 4 million pixels total, 2 MiB normalized JPEG output, and 32 MiB aggregate stored bytes. Rejection changes nothing. Exhausted aggregate capacity returns `413` with a `storage-capacity-exceeded` code, distinct from the `media-limit-exceeded` code for per-image dimensions, pixels, and output, while the servlet-level request and input limits return body-less `413`. Media is stored with the Product record in bounded process memory under one Catalog store lock, served only for the current media ID as `image/jpeg` with `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`, and released on removal or Product deletion. The upload response is built from the snapshot captured by the atomic publication rather than a follow-up read, and stored bytes cannot be mutated through the accessor.
- Decisions: route-based Admin screens with real URLs and no router dependency, keeping the list management-only; staged image selection with create-first-then-upload and edit-first-then-media so a file choice never changes server media by itself; explicit partial-success and uncertain-outcome reporting across the separate field and media requests, with reconciliation by reading the Product and no path that silently duplicates a Product; curated dropdown removed while the nullable `mediaKey` contract, curated mapping, and exact legacy key preservation remain; one image per Product for this MVP; JPEG-only normalized upload with the documented limits; uploaded media in bounded process memory rather than filesystem or external storage, lost together with the Product on restart; explicit media-aware store operations so full `PUT` cannot drop media implicitly; one store lock with coordinator → store lock order preserving the existing `CatalogCartCoordinator` Cart-conflict guarantee and one-way Cart → Catalog dependency; EXIF orientation is stripped and pixels are not rotated, so EXIF-dependent phone photos may appear sideways (owner-approved); [ADR 0004](docs/adr/0004-adopt-product-media-upload.md) supersedes the no-upload decision of [ADR 0003](docs/adr/0003-adopt-optional-product-media-reference.md). No authentication, authorization, hosting, persistence, external media service, or multiple-image model is introduced.
- Agent Verification: backend `./mvnw --batch-mode --no-transfer-progress clean verify` passed 99 tests (media normalizer limits, store accounting/budget/concurrency, duplicate-ID save rejection that preserves the existing Product and its media bytes, latch-controlled upload-response snapshot interleavings against replacement and deletion, stored-byte immutability, MockMvc upload/replace/remove/serve/headers/rejection/Cart-conflict, and constrained-context capacity with the distinct `storage-capacity-exceeded` code); frontend `npm run typecheck`, `npm test` (107 tests across 12 files), and `npm run build` passed, covering route selection including a malformed percent-encoded edit path, the compact list, create with and without an image, create-with-image partial failure and retry with a newly selected file without duplicate creation, create-outcome uncertainty and the reload-with-no-image retry state, staged edit media with Cancel and legacy `mediaKey` preservation, replacement-file retry without a second field update, clear-selection and undo-removal pending-media consistency with no unintended upload or DELETE, media reconciliation, fallback, and thumbnail/preview rendering; the local backend and Vite proxy served `/`, `/admin/products`, `/admin/products/new`, `/admin/products/{id}/edit`, and an unknown Admin path with the application shell, and a real create, image upload, retrieval, and replacement passed through the proxy. The 3 MiB multipart request limit is servlet configuration exercised there because MockMvc bypasses multipart size enforcement.
- Human Verification: Approved on 2026-09-25 based on the owner's report that Human Verification is approved; no individual browser observations were reported, so none are recorded. The owner later reported that the targeted browser recheck of the changed create and edit image flows passed; no individual recheck observations were reported. This is owner-reported human evidence and remains distinct from Agent Verification and CI Verification, which is still pending.
- Delivery: The reviewed change is committed on the short-lived branch `feat/ss-034-product-media-upload` and submitted as a pull request against `main`; CI Verification must pass on the exact final head before merge, and merge requires explicit owner authorization.

## SS-033 — Admin Catalog Management (#55)

- Completed and merged via PR #56 (squash commit `5ac10a4`): a distinct `/admin/products` surface lists Products with ID, name, description, price, and media, filters locally by case-insensitive name, and creates, edits, and deletes Products through `POST`, full-replacement `PUT /api/products/{id}`, and `DELETE /api/products/{id}` after explicit inline confirmation; absent IDs return `404`, and deletion returns `409 Conflict` while the Product is in the current Cart. A successful mutation whose list refresh fails keeps its success message, reports that the change was saved but the list could not be refreshed, and offers a working retry. Frontend routing selects Market, Admin, or a not-found view from `window.location.pathname` with same-origin links and no router dependency; `/admin/products` is navigation only and provides no access control. Product update and deletion are atomic per identity, and the neutral `CatalogCartCoordinator` keeps Catalog unaware of Cart storage with the dependency one-way (Cart → Catalog); the guaranteed invariant is single-process API-path only.

## SS-032 — Implement Checkout vertical slice (#53)

- Completed and merged via PR #54 (squash commit `20b7d537`): Checkout is an editable live view of the current authoritative Cart. Entering Checkout is a local view transition that creates no backend resource; the surface renders the shared editable Cart item row, and `Catalog` remains the single owner of Cart state, so every server response updates quantities, line subtotals, and total. The earlier immutable-snapshot and read-only-review designs were superseded by owner decision. No ADR; follows ADR 0001.

## Local Development Launcher Maintenance (#50)

- Completed and merged via PR #51 (squash commit `729063e`): `scripts/dev.sh` verifies process-group ownership without `ps`, treats a valid `JAVA_HOME` as the authoritative Java selection and normalizes it before appending `/bin` exactly once to the `PATH` it prepends for child processes, refuses to start when the required backend (8080) or frontend (5173) port is already in use, and accepts backend health only while its own backend process group is running.
