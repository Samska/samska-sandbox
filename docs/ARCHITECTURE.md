# Architecture

## Current State

The repository contains a Spring Boot backend application in `backend/`, a React frontend application in `web/`, and a Docker Compose PostgreSQL runtime for local development. Catalog owns a framework-independent Product domain model with an optional media key, Product creation, update, deletion, collection browsing, identity retrieval, media upload, removal, and retrieval, an HTTP adapter, and a temporary in-memory Product store behind an application-owned boundary. Cart is a separate business boundary with a process-local single current Cart, explicit domain rules, Cart HTTP operations, and a Cart store boundary. Cart obtains the minimum Product data it needs through the Catalog-owned `ProductCatalog` application contract and does not access Catalog storage. Product deletion is refused with `409 Conflict` while the Product is in the current Cart; a neutral application coordination component, `CatalogCartCoordinator`, serializes Cart additions and Product deletions under one process-local lock, keeps Catalog unaware of Cart storage, and preserves the one-way Cart-to-Catalog module dependency. That protection is a single-process API-path guarantee, not a cross-process or persistence guarantee. Checkout is a frontend view over the current Cart rather than a backend business boundary: it presents the authoritative Cart response and edits it directly through the existing Cart operations (quantity changes and item removal), updates immediately when the Cart changes, and introduces no Checkout identity or storage. `Cart.snapshot()` captures the Cart's items, total, and revision under one lock, and the Cart API response serializes one snapshot so all three come from the same consistent read; Cart remains the single owner of monetary calculation. Payment is a separate business boundary that owns identified, immutable simulated-payment attempts in a bounded process-local store. Payment initiation serializes through one Payment-store lock and, under that lock, asks Cart for a revision-checked snapshot (`snapshotForRevision`), so the nested lock order is Payment → Cart and a Cart mutation that wins the Cart lock first is reported as `cart-changed` instead of being decided; Cart mutation paths never acquire the Payment lock. An identical attempt ID replays the stored decision, one unchanged Cart revision can hold at most one approved attempt, and the store retains at most 32 attempts without eviction. No real payment, credentials, external provider, or Order creation is involved. Product data, uploaded Product media, Cart data, and payment attempts start empty and are lost on restart. The frontend selects a surface from the browser path without a router dependency: the customer Market at `/`, an Admin Product-management list at `/admin/products`, dedicated Admin create and edit forms at `/admin/products/new` and `/admin/products/{id}/edit`, and a distinct not-found view for other paths; same-origin links produce full-page navigation, so direct entry, reload, and browser history work and returning to the Market refetches Catalog data. The Market keeps a refined storefront presentation, responsive Product browsing, an accessible Cart drawer, an editable Checkout view over the current Cart with an explicit simulated-payment control and a frozen result surface, and local Product and Cart state; focused browse, detail, media, Admin, checkout, and payment components share a small presentation primitive layer for controls and feedback, and the Cart item editing row is shared between the Cart drawer and Checkout. The Admin surface lists Products with local case-insensitive name search, creates, edits, and deletes them, and explains a `409` Cart conflict in place of a deletion; `/admin/products` is navigation only and is not an access-control boundary before authentication and authorization exist. Product media resolves the optional nullable `mediaKey` through a reviewed static mapping to repository-owned local assets, with an intentional monogram fallback when media is absent, unmapped, or fails to load; [ADR 0003](adr/0003-adopt-optional-product-media-reference.md) recorded the curated direction, and [ADR 0004](adr/0004-adopt-product-media-upload.md) supersedes its no-upload decision. The Catalog also stores one validated, re-encoded JPEG per Product beside the Product record in bounded process memory under one store lock; Product responses carry a read-only nullable `uploadedMediaId`, only the current media ID is served (as `image/jpeg` with nosniff and no-store), full `PUT` preserves uploaded media, removal and Product deletion release it and its byte accounting, and uploaded media takes display precedence over curated media or the fallback. Uploaded media is process-local and disappears with the Product on restart. Frontend presentation uses Tailwind CSS v4 through the official Vite plugin: approved visual tokens live in Tailwind `@theme` definitions, component styling uses Tailwind utilities in JSX, and `index.css` retains only base global rules. This styling decision is recorded in [ADR 0002](adr/0002-adopt-tailwind-css-v4-for-frontend-styling.md). Feature-local API adapters own relative request paths, transport handling, response validation, and status-based error translation, while presentation components consume typed request and response data without owning backend business rules. Vite proxies `/api` to the local backend for development only; it does not define production frontend/API routing or a backend CORS policy. The backend has no application persistence, external integrations, or deployment configuration. PostgreSQL readiness is infrastructure evidence only: the backend has no JDBC driver, DataSource, schema, migration, persistence repository, or database health participation. This document records the approved direction for future work; it does not describe a deployed system or unimplemented application behavior.

Order is now an in-process boundary owning immutable, process-local Order records copied from approved Payment attempts. It exposes an application-owned store and HTTP operations for explicit creation and lookup by Order ID or Payment attempt ID. Order creation serializes under its own lock and reads Payment through the Payment-owned `PaymentAttempts` contract (Order → Payment → Cart lock direction; no reverse calls). One attempt produces at most one Order during a backend process lifetime; restart loses both Orders and Payment attempts. [ADR 0006](adr/0006-adopt-order-owned-in-memory-store.md) records the decision.

The frontend journey is attempt-addressed. `/checkout` renders the editable live Cart, and `/checkout/attempts/{attemptId}` resolves the Payment result or Order through the existing read APIs after full-page reload, direct entry, or history navigation. The pathname-based selection is extended with narrowly scoped History API and `popstate` handling; no router dependency is introduced. Route-driven reads are GET-only recovery: an active local Payment or Order operation blocks reads for that attempt, and identity plus generation guards reject stale responses so they cannot replace a pending state or enable transactional actions. Results render from the Payment-captured snapshot or the frozen Order independently of live Cart or Catalog loading, the live Cart is never cleared by Order creation, and one latest-reference UUID in `sessionStorage` is only a discovery hint. [ADR 0007](adr/0007-adopt-attempt-addressed-browser-recovery.md) records the decision.

## Initial Direction

The initial backend is a modular monolith: one deployable application with explicit internal module boundaries, rather than independently deployed services. Catalog is the first implemented boundary and owns Product. The remaining candidate v0.1 modules are:

- Inventory

Payments and Orders are implemented in-process boundaries; Inventory remains a candidate v0.1 module. No separate services or independent databases are implied. Responsibilities, dependencies, persistence ownership, and enforcement approach follow [Architecture Principles](architecture/principles.md).

The initial technology direction uses React and TypeScript with Vite for the web application and Java and Spring Boot for the backend. Docker Compose now provides a local PostgreSQL runtime that future persistence work can use. Physical schemas, module data ownership, persistence libraries, transactions, migrations, application credentials, and backend connectivity remain future decisions tied to actual persistence behavior.

## Evidence-Driven Evolution

Architecture evolves when observed engineering problems justify a change. Examples include catalog read pressure motivating cache evaluation, problematic synchronous processing motivating message-broker evaluation, concurrent stock updates requiring transaction and locking strategy, or independently evolving boundaries motivating service-extraction evaluation.

Redis, RabbitMQ, OpenTelemetry, cloud infrastructure, Kubernetes, and other future technologies are evaluation candidates. They are not current architecture, implementation requirements, or automatic roadmap deliverables.

## Decision Records

Significant, durable architectural decisions must be recorded as Architecture Decision Records (ADRs). The ADR process and template are in [adr/README.md](adr/README.md). The initial direction is recorded in [ADR 0001](adr/0001-adopt-modular-monolith.md), the simulated-payment snapshot model in [ADR 0005](adr/0005-adopt-payment-attempt-store-with-cart-revision.md), and Order ownership and idempotency in [ADR 0006](adr/0006-adopt-order-owned-in-memory-store.md).

The guiding rules for module boundaries and future evolution are in [Architecture Principles](architecture/principles.md).
