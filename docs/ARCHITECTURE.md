# Architecture

## Current State

The repository contains a Spring Boot backend application in `backend/`, a React frontend application in `web/`, and a Docker Compose PostgreSQL runtime for local development. Catalog owns a framework-independent Product domain model with an optional media key, Product creation, update, deletion, collection browsing, identity retrieval, media upload, removal, and retrieval, an HTTP adapter, and a PostgreSQL-backed Product store (`JdbcProductStore`, [ADR 0011](adr/0011-adopt-postgresql-catalog-persistence.md)) behind an application-owned boundary; the in-memory store remains only for the `no-database` test profile. Uploaded media (at most one JPEG per Product, bounded in total) is stored in `product_media`, and the aggregate budget is enforced transactionally under an advisory lock. Product listings carry media IDs without image bytes. Cart is a separate business boundary with a single current Cart persisted in PostgreSQL through the Cart-owned `CartStore` port (`JdbcCartStore`; `InMemoryCartStore` is used only by the `no-database` test profile and pure unit tests), explicit domain rules, and Cart HTTP operations. Every Cart change runs through `CartStore.update` in one transaction under a row lock, so revisions are strictly increasing and no update is lost; a rejected change stores nothing. A Cart line keeps its own Product name and price snapshot and has no foreign key to Catalog, so it can outlive a Product lost on restart ([ADR 0009](adr/0009-adopt-postgresql-cart-persistence.md)). Cart obtains the minimum Product data it needs through the Catalog-owned `ProductCatalog` application contract and does not access Catalog storage. Product deletion is refused with `409 Conflict` while the Product is in the current Cart; a neutral application coordination component, `CatalogCartCoordinator`, serializes Cart additions and Product deletions under one process-local lock (a single-process guarantee; the database row lock separately serializes Cart changes), keeps Catalog unaware of Cart storage, and preserves the one-way Cart-to-Catalog module dependency. That protection is a single-process API-path guarantee, not a cross-process or persistence guarantee. Checkout is a frontend view over the current Cart rather than a backend business boundary: it presents the authoritative Cart response and edits it directly through the existing Cart operations (quantity changes and item removal), updates immediately when the Cart changes, and introduces no Checkout identity or storage. `Cart.snapshot()` captures the Cart's items, total, and revision under one lock, and the Cart API response serializes one snapshot so all three come from the same consistent read; Cart remains the single owner of monetary calculation. There is no Payment boundary: the simulated payment was removed in SS-094 ([ADR 0021](adr/0021-remove-the-simulated-payment.md)), and Checkout places the Order directly. No real payment, credentials, or external provider is involved. The frontend selects a surface from the browser path without a router dependency: the customer Market at `/`, an Admin Product-management list at `/admin/products`, dedicated Admin create and edit forms at `/admin/products/new` and `/admin/products/{id}/edit`, and a distinct not-found view for other paths; same-origin links produce full-page navigation, so direct entry, reload, and browser history work and returning to the Market refetches Catalog data. The Market keeps a refined storefront presentation, responsive Product browsing, an accessible Cart drawer, an editable Checkout view over the current Cart with one Place order action and an Order confirmation, and local Product and Cart state; focused browse, detail, media, Admin, and checkout components share a small presentation primitive layer for controls and feedback, and the Cart item editing row is shared between the Cart drawer and Checkout. The Admin surface lists Products with local case-insensitive name search, creates, edits, and deletes them, and explains a `409` Cart conflict in place of a deletion; `/admin/products` is navigation only and is not an access-control boundary before authentication and authorization exist. Product media resolves the optional nullable `mediaKey` through a reviewed static mapping to repository-owned local assets, with an intentional monogram fallback when media is absent, unmapped, or fails to load; [ADR 0003](adr/0003-adopt-optional-product-media-reference.md) recorded the curated direction, and [ADR 0004](adr/0004-adopt-product-media-upload.md) supersedes its no-upload decision. The Catalog also stores one validated, re-encoded JPEG per Product beside the Product record in bounded process memory under one store lock; Product responses carry a read-only nullable `uploadedMediaId`, only the current media ID is served (as `image/jpeg` with nosniff and no-store), full `PUT` preserves uploaded media, removal and Product deletion release it and its byte accounting, and uploaded media takes display precedence over curated media or the fallback. Uploaded media is stored with its Product in PostgreSQL and is deleted with it. Frontend presentation uses Tailwind CSS v4 through the official Vite plugin: approved visual tokens live in Tailwind `@theme` definitions, component styling uses Tailwind utilities in JSX, and `index.css` retains only base global rules. This styling decision is recorded in [ADR 0002](adr/0002-adopt-tailwind-css-v4-for-frontend-styling.md). Feature-local API adapters own relative request paths, transport handling, response validation, and status-based error translation, while presentation components consume typed request and response data without owning backend business rules. Vite proxies `/api` to the local backend for development only; it does not define production frontend/API routing or a backend CORS policy. The backend has application persistence only for Orders: PostgreSQL is required at startup for the Hikari DataSource, Flyway-managed schema, and JDBC Order store, and database health participates in `/actuator/health`. Orders, the Cart, Products, and uploaded Product media are persisted in PostgreSQL and survive restart. Each Order has a UUID key and a separate unique `order_number` from a database sequence (SS-090, `V10`); the API shows it as `SK-000128`, and the UUID stays the key in URLs. There are no external integrations or deployment configuration. This document records the approved direction for future work; it does not describe a deployed system or unimplemented application behavior.

Order is an in-process module boundary owning immutable Order records copied from the Cart, persisted in PostgreSQL through the Order-owned `OrderStore` port. It exposes HTTP operations to place an Order and to look one up by Order ID. Placing an Order sends a client-generated request ID and the Cart revision the customer reviewed; the store asks Cart for a revision-checked snapshot (Order → Cart direction; a changed Cart is reported as `409 cart-changed`), copies the lines and total into the Order, takes the stock from Inventory and stores everything in one transaction. Items are historical snapshots; the schema has no foreign keys to Product or Cart state. A unique request ID, a replay-first lookup, and that single transaction make placement idempotent across processes and restarts; a concurrent duplicate resolves to the stored Order. The Order service empties the account's Cart once a new Order is stored (replays do not touch it; SS-086). Database unavailability is reported as `503 order-store-unavailable`. [ADR 0006](adr/0006-adopt-order-owned-in-memory-store.md) records the original ownership decision, [ADR 0008](adr/0008-adopt-postgresql-order-persistence.md) the persistence decision, and [ADR 0021](adr/0021-remove-the-simulated-payment.md) the removal of the Payment attempt that used to precede it.

The frontend journey has one Checkout step. `/checkout` renders the editable live Cart with a Place order action; on success the same surface shows the Order confirmation with its number and a link to tracking. The client keeps the request ID while a result is unconfirmed, so pressing Place order again returns the same Order, and it starts a new one after a definite refusal. The pathname-based selection uses narrowly scoped History API and `popstate` handling; no router dependency is introduced. The attempt-addressed recovery surfaces and the latest-reference `sessionStorage` hint of [ADR 0007](adr/0007-adopt-attempt-addressed-browser-recovery.md) are removed with the Payment attempt.
Orders and Inventory are in-process module boundaries persisted in PostgreSQL. No separate services or independent databases are implied. Responsibilities, dependencies, persistence ownership, and enforcement approach follow [Architecture Principles](architecture/principles.md).

The initial technology direction uses React and TypeScript with Vite for the web application and Java and Spring Boot for the backend. Docker Compose provides the local PostgreSQL runtime used by the Order boundary. The Order schema, JDBC/Flyway choice, transactions, local application credentials, and connectivity are recorded in [ADR 0008](adr/0008-adopt-postgresql-order-persistence.md); persistence decisions for other modules remain future work tied to actual behavior.

## Evidence-Driven Evolution

Architecture evolves when observed engineering problems justify a change. Examples include catalog read pressure motivating cache evaluation, problematic synchronous processing motivating message-broker evaluation, concurrent stock updates requiring transaction and locking strategy, or independently evolving boundaries motivating service-extraction evaluation.

Redis, RabbitMQ, OpenTelemetry, cloud infrastructure, Kubernetes, and other future technologies are evaluation candidates. They are not current architecture, implementation requirements, or automatic roadmap deliverables.
