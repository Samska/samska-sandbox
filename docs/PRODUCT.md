# Product

## Purpose

Samska Sandbox is a public, non-commercial educational engineering platform. It uses a fictional commerce and logistics domain to progressively practice real-world engineering disciplines, including software, backend, frontend, mobile, quality, security, DevOps, platform, SRE, observability, performance, data, architecture, and AI-assisted software engineering.

The project's non-commercial purpose does not restrict downstream use of the Apache-2.0 licensed source code.

## Current Scope

The repository currently contains Java and React applications, a local PostgreSQL runtime, a Catalog boundary with a framework-independent Product domain model, and a Cart boundary; Checkout is an editable frontend view of the current Cart. Each Product has a validated name, description, price, and optional media key, and the Catalog HTTP API supports Product creation, collection browsing, identity retrieval, full update, and deletion with that data. The React UI provides a refined commerce storefront: responsive Product browsing with consistent product cards, a selectable Product detail view with curated local media or an intentional monogram fallback and focus return to browsing, unified loading, pending, success, and error feedback, an accessible Cart drawer, quantity updates, item removal, and server-calculated totals. A non-empty Cart exposes a Checkout view that presents the current Cart's Product identities, names, unit prices, quantities, line subtotals, and total, and lets the user edit quantities and remove items directly using the existing Cart operations; every change is reflected immediately from the server response. The immutable transactional snapshot is now provided by Payment Simulator: the Checkout surface offers an explicit local-demo outcome (Approve, Decline, or Temporary failure) and a Simulate payment action, the backend captures a revision-checked immutable snapshot of the current Cart, and the simulated decision is owned by a bounded process-local Payment store with same-ID replay, one approval per unchanged Cart revision, and GET reconciliation. No real payment, credentials, or Order is created, and attempts are lost on backend restart. The application also provides a distinct Admin Product-management surface: `/admin/products` is a compact management list with local case-insensitive name search, thumbnails, price, and Edit/Delete actions; `/admin/products/new` hosts a dedicated creation form and `/admin/products/{id}/edit` a matching edit form, each with Name, Description, Price, and a staged Product image section. Deletion requires explicit confirmation and is refused with `409 Conflict` while the Product is in the current Cart; absent IDs return `404`. Creating or saving Product details and uploading or removing an image are separate requests: the forms report partial success accurately, never claim an unconfirmed result, and offer image retry without repeating the field operation. The Admin surface lets an administrator upload, replace, and remove one JPEG image per Product; uploads are validated and re-encoded server-side against fixed limits (3 MiB multipart request, 2 MiB input file, 2048 pixels per side, 4 million pixels, 2 MiB normalized output, 32 MiB aggregate stored bytes), stored only in bounded backend process memory, and lost with the Product on restart. Uploaded media takes display precedence in Market cards and Product detail, invalid uploads leave the current image unchanged, and removing an upload reveals the retained curated media or the monogram fallback. Re-encoding strips EXIF orientation, so some phone photos can appear sideways. The Market at `/` contains no Product setup or identity-lookup controls. `/admin/products` is a navigation path, not an access-control boundary, and provides no security before authentication and authorization exist. Catalog and Cart data are temporary and process-local; Checkout holds no server-side state, and simulated payment attempts, including their captured snapshots and duplicate protection, live only in the current backend process. Orders and their items are persisted in PostgreSQL and survive a backend restart; Product, uploaded media, Cart, and payment-attempt data remain process-local and are lost on restart. There is no authentication, real payment processing, or deployment environment.

Order creation now adds an explicit action after a confirmed approved attempt. It copies the Payment-captured items and total into an immutable Order persisted in PostgreSQL with its items; repeat creation for the same attempt replays the same result, including after a backend restart. The Order-specific 32-order guard is removed. An uncertain POST is reconciled by Order lookup, then Payment lookup after Order `404`; two `404` lookups do not prove restart. Creating an Order does not change Cart or move real money. The owner observed the main browser flow (creation, in-app navigation, and the frozen Order after a Cart change); API replay, uncertain-response recovery, and accessibility remain pending real-browser checks. This capability is implemented and merged through PR #67.

The First Order journey is complete and merged through PR #70. `/checkout` is an addressable editable Cart surface, and `/checkout/attempts/{attemptId}` resolves the simulated payment attempt or its Order through read-only lookups after a full-page reload, direct entry, or browser history. Recovery never resends a Payment or Order request, renders from the captured snapshot or frozen Order even when live Cart or Catalog loading fails, and requires an explicit choice before a new journey replaces an unresolved reference. Creating an Order still does not clear the live Cart, and one browser-held reference is only a discovery hint. Reload, replay, uncertain-response, and accessibility behavior were exercised in the owner-reported browser verification recorded before merge. Cart and Payment remain process-local with their existing limits; Orders are durable.

Market Product-name search (SS-044, #81) is complete and merged via PR #82 (squash `8b32000`, merged 2026-10-15): a local, case- and accent-insensitive substring filter on `Product.name` in the Market, held in `Catalog` state while `Catalog` is mounted so the term survives Product details and Market → Checkout → Back to Market, and reset only on full-page reload. The term is never written to the URL, history, sessionStorage, localStorage, or logs, and never sent to the API — `GET /api/products` is unchanged and the filter runs entirely in the browser over the already-loaded list. The displayed Product name is never re-formatted. By decision, Admin keeps its accent-sensitive filter (`String.prototype.toLowerCase` only); the documented difference is that Market is accent-insensitive and Admin is accent-sensitive. The Market search field is hidden while Products are loading, on load error, and when the Catalog is empty, and remains visible on a zero-match result; the count badge becomes the single polite live region, the zero-match block is plain text, and "Clear search" restores the full list without a new API request and returns focus to the search input. The existing focus-return mechanism for the originating View details control is reused; if that control is no longer in the map on return, focus falls back to the search input.

## Initial Product Milestone

v0.1.0, "First Order", will eventually enable a user to:

1. Open the web application.
2. Browse products.
3. Add a product to a cart.
4. Check out.
5. Receive a simulated payment decision.
6. Create an order.
7. View an order confirmation.

Steps 1 through 7 are implemented and the journey is merged through PR #70, including attempt-addressed result recovery after reload, direct entry, and history. Agent Verification and the owner-reported browser verification remain distinct records. SS-037's original limited Human Verification record is unchanged, and its unobserved API replay, uncertain-response recovery, and accessibility checks are not retroactively marked as passed for SS-037.

Docker Compose provides local PostgreSQL, which the backend requires for Order persistence. The backend and frontend are not containerized. A future full-application workflow should remain simple when its behavior is justified.

## Future Domain Scope

The platform may evolve to cover customers, catalog, cart, checkout, orders, inventory, simulated payments, delivery, couriers, notifications, fraud/risk simulation, analytics, and a simulation engine. These are opportunities for progressive learning, not commitments to implement every domain.

## Product Constraints

- All data must be synthetic. No real customer data is permitted.
- Payments must be simulated. No real financial transactions are permitted.
- A future public demo must be constrained and disposable.
- AI agents may produce or modify code, but human accountability for decisions, review, validation, risk assessment, and understanding remains mandatory.

## Explicit Non-Goals

- Operating a real commerce business.
- Processing real payments.
- Storing or exposing real customer data.
- Building microservices before engineering evidence justifies extraction.
- Treating the roadmap as a mandatory technology adoption checklist.

See [the roadmap](ROADMAP.md) for planned work and [AI governance](AI-GOVERNANCE.md) for delivery responsibilities.
